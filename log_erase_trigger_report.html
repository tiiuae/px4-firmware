    1Executive summary#

    PX4 can erase all onboard logs today, but only via the MAVLink LOG_ERASE message. The erase routine is a recursive unlink()/rmdir() walk that is private to MavlinkLogHandler and not reachable from another module. There is no logger clear shell command, no log_erase system command, and no shared log-utility library.

    On Saluki-NXP93 the NuttX px4_arch_gpioread() API is available, edge interrupts are enabled, and the board already ships a polled-GPIO-input driver (safety_button) that is a direct structural template for a hold-to-trigger input. The recommended approach — factor the erase walk into a shared log_utils library and add a small log_erase_trigger work-queue module that polls a free GPIO — is viable on this target.

    Two things to carry forward from the caveats: the gpio shell command is not compiled into this board's firmware, so pin bring-up must be done in code; and the erase must be interlocked against the logger, for which a ready-made uORB liveness signal already exists (§5.3).

    5.2 Logs are encrypted on this board

    CONFIG_BOARD_CRYPTO=y — saluki-nxp93/default.px4board:3
    param set-default SDLOG_EXCH_KEY 2 / SDLOG_KEY 3 — saluki-nxp93/init/rc.board_defaults:31-32

    What this does and does not imply. Encryption changes the content of log files and adds key-index parameters. It does not make logging continuous, and it has no bearing on whether a directory is safe to delete: rc.board_defaults sets only the two key indices and does not override SDLOG_MODE, so the stock arm-gated logging behaviour applies.

    The operational point that matters: erased logs on this board are unrecoverable by design, and any partially-written encrypted file removed mid-flight is simply gone. That argues for the interlock in §5.3 — which is needed regardless of encryption.

    5.3 The logger interlock — a ready-made liveness signal

    The hazard is not arming state — it is deleting files under an open writer. logger on starts logging regardless of arming, so "disarmed" alone is not a sufficient guard:

    set_arm_override(true) / (false) at logger.cpp:162 and :167 — shown in §3.

    logger_status is published at 1 Hz only while the writer is started, which makes its freshness a direct proxy for "the logger is writing right now":

    Recommended interlock — no new plumbing required:

    • Subscribe to ORB_ID(logger_status) (topic defined in msg/LoggerStatus.msg; published multi-instance, one per LogType).
    • Treat any instance updated within the last ~2.5 s as logger active → refuse to erase. The 1 Hz cadence at logger.cpp:1072 makes a 2–3 s staleness window safe against jitter without being sluggish.
    • Additionally require disarmed (vehicle_status) as a belt-and-braces condition, and require the GPIO hold to complete after both conditions are already true.
    • Optionally issue logger off semantics first if you want the trigger to work while logging — but the safer default is refuse-and-signal, not stop-and-delete.

    Note LoggerStatus.msg has no is_logging field — liveness is carried by the publication itself, so check message freshness rather than a flag.
